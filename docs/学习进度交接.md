### 5.5 当前正在学习：Spring Boot 后端基础

项目已经从“调用和测试别人提供的接口”推进到“自己实现真实接口”。当前使用 Spring Boot 3.5.16、Java 21 和 TestNG。

已完成：

- `JavaTestStudyApplication`：Spring Boot 启动类。
- 健康检查：`GET /api/health`，理解最简单的 Controller 和 MockMvc 测试。
- 用户接口：
  - `GET /api/users`：返回按 ID 排序的用户列表；
  - `GET /api/users/{id}`：存在返回 200，不存在返回 404；
  - `POST /api/users`：创建用户并返回 201；
  - `PUT /api/users/{id}`：更新用户，存在返回 200，不存在返回 404；
  - `DELETE /api/users/{id}`：成功返回 204，不存在返回 404。
- 请求/响应对象：`CreateUserRequest`、`UpdateUserRequest`、`UserResponse`，使用 Java `record`。
- 参数校验：`@Valid` 配合 `@NotBlank`；空字符串、纯空格或 null 会被 Spring 拒绝并返回 400。
- 统一异常响应：`ApiErrorResponse` 固定返回 `status/code/message/path`；`GlobalExceptionHandler` 使用 `@RestControllerAdvice` 统一处理参数校验错误和用户不存在异常。
- 业务异常：`UserNotFoundException` 由 Service 在查询、更新、删除不存在的用户时抛出，再由全局异常处理器转换为 404 JSON；Controller 不再重复编写 404 分支。
- 用户名唯一业务规则：创建或更新成已存在的用户名时抛出 `UserAlreadyExistsException`，全局异常处理器返回 `409 Conflict` 和 `USERNAME_ALREADY_EXISTS`。
- `UserServiceTest` 使用 Mockito 创建假的 `UserRepository`，通过 `when(...).thenReturn(...)` 控制依赖返回，通过 `verify(...)` 和 `never()` 验证调用及不应发生的调用；覆盖查询、创建、更新、删除的成功和失败场景，该测试不启动 Spring 上下文。
- 用户名唯一性采用两层保护：Service 先查询并给出友好业务错误，数据库 `UNIQUE` 索引负责并发场景的最终兜底；Service 会把 JDBC 的 `DuplicateKeyException` 转换为 `UserAlreadyExistsException`，因此接口仍统一返回 409，并保留原异常作为 cause 便于排查。
- `UserServiceTest` 的 `@BeforeMethod(alwaysRun = true)` 必须保留：回归套件按 `regression` 分组筛选时，`alwaysRun` 保证 mock 初始化不会被跳过。
- 三层结构：

  ```text
  UserController（HTTP请求和响应）
          ↓
  UserService（业务层）
          ↓
  UserRepository（数据访问层）
          ├─ 默认 Profile：InMemoryUserRepository → ConcurrentHashMap
          └─ mysql Profile：JdbcUserRepository → MySQL app_users 表
  ```

- `UserRepository` 是数据访问接口；默认实现 `InMemoryUserRepository` 使用 `ConcurrentHashMap` 保存用户、`AtomicLong` 生成 ID，并通过 Stream 按 ID 排序。
- `InMemoryUserRepository` 使用 `@Profile("!mysql")`；`JdbcUserRepository` 使用 `@Profile("mysql")`。启用 `mysql` Profile 后，Spring 会把 Service 依赖的实现从内存版切换为 JDBC 版，Controller 和 Service 不需要修改。
- 已引入 Spring JDBC 和运行时 MySQL 驱动；`JdbcUserRepository` 使用 `JdbcTemplate` 和参数占位符完成用户 CRUD，并使用 `GeneratedKeyHolder` 取得 MySQL 自增主键。
- MySQL 配置位于 `application-mysql.yml`：URL、用户名可由环境变量覆盖，密码只从 `DB_PASSWORD` 读取，禁止写进配置文件。`spring.sql.init.mode` 为 `never`，表结构由管理员账号一次性执行建表脚本，运行账号 `test_automation` 只负责业务数据读写。
- 新建应用专用的 `app_users` 表，避免与之前数据库自动化使用的 `test_users` 基线数据混用；表中没有物理外键。
- `JdbcUserRepositoryTest` 使用 H2 内存数据库的 MySQL 兼容模式测试真实 SQL 和行映射，不依赖本机 MySQL，也不会修改学习者原有数据。
- `SpringMysqlProfileIntegrationTest` 使用 `mysql` Profile 启动非 Web Spring 上下文，确认注入的是 `JdbcUserRepository`，并在本机 MySQL 中完成创建、查询、更新、删除；临时用户名使用 UUID，测试结束后兜底清理。
- Spring 依赖通过构造方法注入：Controller 依赖 Service，Service 依赖 Repository。
- `UserControllerTest` 使用 MockMvc 在同一 JVM 中验证 Controller → Service → Repository，不需要启动真实网络端口。
- 已理解 MockMvc、RestAssured、WireMock 的区别：MockMvc 测本项目 Spring MVC；RestAssured 从外部发 HTTP 请求；WireMock 是预设响应的模拟服务，不是真实业务后端。

### 6.3 JaCoCo 覆盖率与 CI 质量门禁：已完成并实践

- 已把一小部分可复用、无 TestNG 依赖的框架能力移入 `src/main/java`，使其成为 JaCoCo 的统计对象；测试场景、WireMock 和真实数据库测试仍在 `src/test/java`。
- 已添加 `jacoco-maven-plugin`（版本由 `jacoco.version` 集中管理）：
  - `prepare-agent`：在测试前记录哪些主代码被执行；
  - `report`：在 `verify` 生成 HTML/XML 报告；
  - `check`：在 `verify` 检查整个项目的行覆盖率，当前最低要求为 **80%**。
- 关键命令：

  ```bash
  mvn verify
  ```

  它不只是执行测试；还会在测试通过后生成覆盖率报告，并执行覆盖率门禁。报告入口为 `target/site/jacoco/index.html`，可直接用浏览器打开。
- 已理解 JaCoCo 页面中的 Instruction、Branch、Line、Method、Class 覆盖率；覆盖率表示代码是否被执行过，**不等于** 测试一定没有业务缺陷。
- 已为 `TokenUtil`、用户 ID、分页、角色、用户名排序方向、超时参数等纯校验能力补充单元测试。
- 已解决 IDEA 中 Surefire 配置爆红：将 Surefire 版本集中为 `${surefire.version}`，而不是在多个 Profile 中重复写版本。
- 已创建并合并 PR #3：`test-coverage -> main`，加入 JaCoCo 覆盖率门禁。
- 随后发现并修复 CI 的关键缺口：原 CI 使用 `mvn ... test`，不会进入 JaCoCo 绑定的 `verify` 阶段。因此将回归套件改为：

  ```bash
  mvn --batch-mode -Pregression-test verify
  ```

  并上传 `target/site/jacoco` 为 `jacoco-html-report` Artifact。这样 PR 的 CI 会真正因覆盖率低于 80% 而失败。
- 此 CI 修复已通过独立分支、PR、必需检查并合并进 `main`；合并后已删除远程功能分支。后续仍必须遵守“功能分支 → PR → CI 通过 → 合并”的流程。

## 8. 继续教学时的重要原则

- 代码默认由 Codex 编写；一次可推进两个紧密相关、可验证的小目标。完成后解释“代码做了什么、为什么这样设计、企业里的价值”。
- 学习者询问代码时，优先按执行顺序解释，并标出当前文件的准确行号。
- 对真实数据库操作必须强调测试数据隔离和清理；不要删除用户原有数据。
- 数据库关系只使用逻辑外键，不新增物理 `FOREIGN KEY`；仍需通过代码校验、联合主键/唯一约束、索引和清理顺序保证一致性。
- 不要让学习者把密码、Token 写进 Java、YAML、Git 或 Allure。
- 使用 WireMock 时说明：它模拟外部服务，不能代替真实后端或真实数据落库验证。
- 每次添加真实 DB 测试后，提醒使用 `mvn clean -Pdatabase-test test`；报告前用 `mvn allure:serve`。
- Allure 报告中的数据库附件在用例详情的 `Test body` 下，以文件图标/“数据库操作：...”显示。
- 学习者遇到报错时，应先解释报错最关键的一行，再给最小修改方案，而不是直接丢出大量代码。
